# Lyria 出力 MP3 の調査と無劣化トリム方式

Google Gemini Lyria が書き出す MP3 を解析し、再エンコードなしでサンプル精度のトリムができるかを検証した記録。
調査日: 2026-11-09。対象: `samples/` の 4 ファイル(2026-11-07〜08 生成)。

## 1. ファイル構造(4 本とも共通)

| 項目 | 内容 |
|---|---|
| ストリーム | MPEG-1 Layer III、CBR 192kbps、44.1kHz、joint stereo、CRC なし |
| フレーム長 | 626 バイト(padding ビットありで 627 バイト) |
| Xing / Info / VBRI / LAME ヘッダ | なし(エンコーダ遅延・パディング情報なし) |
| 先頭タグ | ID3v2.3 が 1 つ。中身は `GEOB` フレーム(MIME `application/c2pa`)1 つのみ、約 6KB |
| 末尾 | ID3v1 なし、最終フレーム以降のデータなし |
| ビットリザーバ | ほぼ全フレームで使用(`main_data_begin > 0` が 96〜99%) |

### C2PA マニフェスト

`GEOB` には Google が署名した C2PA マニフェストストアが入っている。主な中身:

- `c2pa.created`: "Created by Google Generative AI."
- `c2pa.edited`: "Applied imperceptible SynthID watermark."
- `c2pa.hash.data`: ファイル本体のバイト列に対するハッシュ(hard binding)

トリムするとハッシュが一致しなくなり、検証に失敗する。K!LN は署名し直せない。

## 2. 検証結果

ffmpeg でデコードした PCM を、元ファイルのデコード結果と比べた。

1. **フレーム境界でそのまま切る**: 切った位置から 2 フレームが壊れる(RMS 誤差が信号と同程度)。原因はビットリザーバ(前のフレームのデータを参照する)と MDCT のオーバーラップ。
2. **切る位置より 2 フレーム手前から含める**: 目的のフレーム以降が元ファイルとビット一致する(2 ファイル × 2 か所で確認)。
3. **2 に加えて先頭に Info + LAME ヘッダのフレームを付け、encoder delay / padding で余分な部分を指定する**: 任意のサンプル位置で切った結果が、元ファイルのデコード結果の該当区間と **f32 でビット一致**し、長さも一致した(端数 0 / 300 / 1151 サンプルで確認)。s16 出力では ±1 の差が十数サンプル出るが、これは ffmpeg の量子化によるもの。

### ffmpeg の挙動で分かったこと

- 先頭でスキップされるサンプル数 = LAME タグの `delay` + 529(デコーダ遅延)
- 末尾の削除には Xing の `frames` フィールドと LAME タグの `padding` を使う。デコーダ出力上の終わり = `frames * spf - padding + 529`
- LAME タグのエンコーダ名が `LAME` / `Lavf` / `Lavc` のどれかで始まらないと、delay / padding を無視する
- 入力をパイプで渡すとファイルサイズが分からず、末尾の padding が効かない(ファイルなら効く)

## 3. ブラウザでの検証(2026-11-09)

トリム済みファイルをブラウザで `OfflineAudioContext(44100Hz).decodeAudioData` に通し、同じブラウザで元ファイルをデコードした結果と比べた。合わせて `<audio>` 要素の `duration` も記録した。

| 変種 | Chrome 156 | Safari 26.6.2 |
|---|---|---|
| Info + LAME タグ(エンコーダ名 `LAME…`) | ビット一致・長さ一致 | 長さは一致、**開始が 529 サンプル早い** |
| Info + LAME タグ(エンコーダ名 `KILN`) | 補正なし(余分な 2 フレームが鳴る) | 上と同じ(エンコーダ名を見ていない) |
| Info なし | 補正なし | 補正なし |
| LAME タグ + ID3v2 の `iTunSMPB`(priming = delay + 529) | ビット一致・長さ一致 | 開始は一致、**末尾 29 サンプルが不一致** |
| 上記 + 末尾に 1 フレーム余分に含める | **ビット一致・長さ一致** | **ビット一致・長さ一致** |

分かったこと:

- Chrome は ffmpeg と同じ挙動(LAME タグを読み、エンコーダ名が `LAME` / `Lavf` / `Lavc` で始まる必要がある。`iTunSMPB` は無視)
- Safari は LAME タグの delay / padding を読むが、ffmpeg と違い 529 を足さない。エンコーダ名は見ない。`iTunSMPB` があればそちらを優先する
- Safari のデコーダは、デコーダ出力(連結したフレーム全体、`F * spf` サンプル)の末尾約 529 サンプルが正しく出ない。そのため末尾に 1 フレーム余分に含め、その部分を padding で落とす必要がある
  - 表の「末尾 29 サンプルが不一致」はこの影響。検証した区間では、切り出したい範囲の終わりがデコーダ出力の末尾から 500 サンプル手前(462604 / 463104)にあり、不正確な末尾 529 サンプルと 29 サンプルだけ重なった
  - LAME タグだけの変種で末尾が一致したのは、開始が 529 サンプル早いぶん終わりも 529 サンプル早く、重ならなかったため
  - 末尾 529 サンプルという値は、上の 1 回の測定から推定したもの
- Safari の `<audio>` の `duration` は、どの変種でも連結したフレーム全体の長さ(`F * spf`。Info フレームは含まない)を返し、delay / padding を反映しない。元ファイル全体の長さではない。Chrome は delay / padding を反映した長さを返す
- `<audio>` で再生したときに、実際に先頭・末尾が切られるかは未確認(確認したのは `decodeAudioData` だけ)
- Firefox は未インストールのため未確認

## 4. トリム方式(検証済みの手順)

Lyria の MP3 で検証した手順。実装ではこれを一般化している(§5)。

切り出す区間を元ファイルのデコーダ出力上のサンプル位置 `[s0, e0)` で指定し、`spf = 1152`、`N = e0 - s0` とする。

1. 開始フレーム `K = floor(s0 / spf)`、端数 `a = s0 - K * spf` を求める
2. フレーム `K - 2` から、最後のサンプル `e0 - 1` を含むフレーム(`floor((e0 - 1) / spf)`)の **1 つ後** までをそのまま連結する(ファイルの先頭・末尾付近では、ある分だけ含める)。連結したフレーム数を `F`、先頭に余分に含めたフレーム数を `lead` とする
3. 先頭に Info フレームを付ける
   - フレームヘッダは元ストリームと同じ設定(padding ビットなし)
   - Xing 部: `Info` タグ、フラグは frames / bytes / TOC / quality の 4 つすべて(LAME タグが標準位置の +120 に来るようにするため)
     - frames: `F`(Info フレーム自身は数えない。ffmpeg はデコーダ出力上の音声の終わりを `frames * spf - padding + 529` とするので、`F + 1` にすると末尾が 1152 サンプルずれる)
     - bytes: Info フレームと連結した `F` フレームの合計バイト数(前に付ける ID3v2 タグは含めない)
     - TOC: CBR なので線形(`i` 番目に `floor(i * 256 / 100)`)
     - quality: 0
   - LAME 部: `delay = lead * spf + a - 529`、`padding = F * spf - delay - N`、エンコーダ名は `LAMEK!LN `(9 バイト。末尾は空白で埋める)
   - LAME タグの CRC-16 を計算して書く(フレーム先頭から 190 バイト分)
4. さらにその前に ID3v2.3 タグを付け、`COMM` フレームを 1 つだけ入れる(iTunes 互換の形式。検証で使ったもの)
   - タグヘッダ: `ID3` + バージョン 3.0、フラグ 0(非同期化なし)、サイズは syncsafe 整数
   - フレーム: ID `COMM`、フラグ 0、テキストエンコーディング `0x00`(ISO-8859-1)、言語 `eng`、説明 `iTunSMPB` + NUL
   - 値(末尾 NUL なし): `" 00000000 PPPPPPPP QQQQQQQQ NNNNNNNNNNNNNNNN"` に `" 00000000"` を 8 回続けた 12 フィールド。16 進数は大文字
     - `PPPPPPPP`: `priming = delay + 529`(8 桁)
     - `QQQQQQQQ`: `padding = F * spf - priming - N`(8 桁)。元ファイル上での連結の終端位置を `end` とすると `end - e0` に等しく、負にはならない
     - `NNNNNNNNNNNNNNNN`: トリム後の有効サンプル数 `N`(`= e0 - s0`。元ファイルの総サンプル数ではない。16 桁)
   - C2PA の `GEOB` は付けない

`delay` と `padding` はどちらも 12bit(0〜4095)の範囲に収まる。

注意:

- `s0 < 529` の場合、`delay` が負になる。LAME タグ付きの出力では先頭 529 サンプル(デコーダ遅延ぶん)を再現できないため、`s0` は 529 以上に切り上げる。この区間は元ファイルでも実質無音
- 元ファイルの末尾まで切る場合は余分な末尾フレームがないため、Safari では最後の約 529 サンプルが正しく出ない。元ファイルを Safari で再生した場合と同じ条件なので、許容する

## 5. 実装での一般化(2026-11-09)

§4 は Lyria の MP3(タグなし、CBR 192kbps、ステレオ)で検証した手順。`kiln trim`(`src/mp3/`)では、Lyria 以外の MPEG-1 Layer III も扱えるよう、次のように一般化した。

### 5.1 入力

- 扱うのは MPEG-1 Layer III(1 フレーム 1152 サンプル、32 / 44.1 / 48kHz)だけ。MPEG-2 / 2.5、Layer I / II、free format は `UnsupportedFormat` のエラーにする
- 先頭の ID3v2 タグ(複数可、v2.4 のフッタ付きも可)は読み飛ばし、出力には引き継がない(C2PA の `GEOB` を含め、`iTunSMPB` の `COMM` 以外は付けない)
- 音声フレームは、最初のフレームから連続している分だけを使う。フレームが途切れたところ、またはサンプルレートやチャンネル数が変わったところを終わりとみなす(末尾の ID3v1 / APE タグもここで除かれる)
- 最初のフレームが Xing / Info / VBRI のヘッダなら、音声フレームに数えない
- **位置の基準(タイムライン)**: ffmpeg がデコードしたときの先頭を 0 とするサンプル位置で指定する
  - LAME タグ付きの入力(エンコーダ名が `LAME` / `Lavf` / `Lavc` で始まるもの。ffmpeg と同じ条件): タイムラインの 0 はデコーダ出力上の `delay + 529`。長さは `frames * spf - max(padding, 529) + 529 - (delay + 529)`(ffmpeg は padding が 529 未満なら末尾を落とさない)
  - それ以外(Lyria を含む): デコーダ出力そのまま。長さは `frames * spf`
- 区間は丸める: タグなしの入力では先頭を 529 以上に切り上げ(§4 の注意)、末尾はタイムラインの長さで切り詰める。丸めた後の区間が空ならエラーにする

### 5.2 開始フレームの手前に含めるフレーム数

§4 の手順 2 では 2 フレーム手前(`K - 2`)から含めたが、2 フレームで足りるのはビットリザーバが 1 フレームに収まる場合だけ。実装では次のように決める。

- 開始フレーム `K` を正しくデコードするには、1 つ前のフレーム `K - 1`(MDCT のオーバーラップ)が正しくデコードされている必要がある。そのためには、`K - 1` の `main_data_begin` バイトのビットリザーバを含むフレームまで遡る
- 遡ったフレーム数(`K - 1` を含む)を `lead` とし、検証した 2 フレームを下限にする(ファイルの先頭付近では、ある分だけ)
- 低ビットレート(目安としてステレオ 80kbps 以下、モノラル 48kbps 以下)では遡るフレームが 4 つ以上になり、`delay = lead * spf + a - 529` が LAME タグの 12bit(4095)に収まらないことがある。そのときは遡る代わりに、**carrier** を `K - 1` の前に置き、`lead = 2` にする
  - carrier は新しく作る無音のフレーム。ヘッダは `K - 1` と同じ設定(padding なし、CRC なし)で、ビットレートはメインデータ領域に `main_data_begin` バイトが収まる最小のもの。サイド情報はすべて 0(`main_data_begin = 0`、音声データなし)
  - メインデータ領域の末尾に、元のストリームで `K - 1` の直前にあったメインデータ領域の末尾 `main_data_begin` バイトを置く。デコーダから見ると、`K - 1` が参照するビットリザーバの中身は元と同じになる
  - carrier を使わずに `lead` を 12bit に収まる範囲で打ち切ると、開始直後の数百〜2000 サンプルほどが元のデコード結果と一致しなかった(48kbps モノラルで確認)

### 5.3 Info フレーム

- ヘッダは連結した最初のフレームと同じ設定で、ビットレートだけを次のように決める
  - 連結したフレーム(carrier を含む)のビットレートがすべて同じ(CBR)なら、そのビットレート。タグは `Info`、TOC は §4 と同じく線形
  - 揃っていなければ(VBR)最小のビットレートから始める。タグは `Xing`、TOC は連結した音声フレームの実際の位置から作る(`i` 番目は、`i`% の位置のフレームが音声フレーム全体のバイト数のどこから始まるかの 256 分率。LAME と同じく Info フレームは含めない)
  - LAME タグまで収まらないフレーム長(ステレオで 192 バイト、モノラルで 177 バイト未満)なら、収まるまでビットレートを上げる(例: 48kHz / 48kbps のフレームは 144 バイトなので、Info フレームは 64kbps にする)
- Xing 部の位置はヘッダ + サイド情報の直後(ステレオで 36 バイト目、モノラルで 21 バイト目)
- LAME タグの CRC-16 は、フレーム先頭から CRC フィールドの直前まで(ステレオで 190 バイト、モノラルで 175 バイト)

### 5.4 実装の検証結果

ffmpeg でデコードした PCM を、元ファイルのデコード結果の該当区間と f32 で比べた(区間は端数 0 / 300 / 1151、末尾まで、乱数で選んだ位置など)。

- `testdata/` の 4 本、Lyria の実ファイル 4 本、lame で作った追加の 6 本(32kbps の 44.1kHz と 48kHz、64 / 128 / 320kbps、CRC 付き、VBR -V 9。一部は LAME タグ付き)の計 14 本 126 区間で、すべてビット一致・長さ一致
- Chrome 156 と Safari 26.6.2(どちらも `decodeAudioData`)でも、同じ 7 区間(carrier を使う 3 区間を含む)でトリム結果の長さが一致し、元ファイルのデコード結果ともビット一致した
- ただし Safari では、LAME タグ付きの元ファイル 2 本(`cbr128-lame`、`vbr-lame`)で、一致する位置が指定した位置より 529 サンプル後ろだった(§6)。タグなしの入力と、32kbps のため LAME がタグを書かなかった `s32-lame` では、ずれはなかった

## 6. 未確認・未決定

- Firefox での挙動(未インストール)
- Safari の `<audio>` 要素で再生したときに頭出し・末尾カットが効くか
- エンコーダ名 `LAMEK!LN ` の影響: `LAME` の後に数字以外が続くため、`LAME3.xx` をバージョンとして解釈するデコーダ(mpg123 など)が、未知のタグとみなしたり、別の補正を当てたりするおそれがある。検証した ffmpeg / Chrome / Safari では `LAME3.100` と同じ結果だった
- **既知の差: LAME タグ付きの入力と Safari の位置**: Safari は LAME タグ付きの元ファイルを `delay` だけずらして(529 を足さずに)デコードする(§3)ため、ffmpeg より 529 サンプル多く頭から再生する。kiln の位置は ffmpeg のタイムライン(§5.1)のままにしているので、Safari で元ファイルを再生して選んだ位置で切ると、トリム結果は 529 サンプル(44.1kHz で約 12ms)後ろにずれる(§5.4 で確認)。トリム結果自体は `iTunSMPB` があるため Safari でも長さ・中身とも正しい。タグなしの入力(Lyria を含む)ではずれない
- 入力の ID3v2 にある `iTunSMPB` は読まない(LAME タグだけを見る)
