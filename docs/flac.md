# FLAC

FLAC の読み込み(`src/flac.zig`、`src/flac/` の `bits` / `frame` / `metadata` / `stream` / `decoder`)と書き出し(`encoder` / `lpc`。§6)の設計と検証の記録。FLAC → FLAC の切り出しは別の PR で作る(方針は [`draft.md`](draft.md) §2.6)。

## 1. 扱う範囲と出所

- 仕様は RFC 9639(Free Lossless Audio Codec)。規格の数表はなく、コードは RFC から書いた(外部のコードや表は取り込んでいない)
- CRC は Zig の標準ライブラリを使う(フレームヘッダの CRC-8 は `std.hash.crc.@"CRC-8/SMBUS"`、フレームの CRC-16 は `@"CRC-16/UMTS"`)
- 扱うのはネイティブの FLAC(`fLaC` で始まるもの)だけ。先頭に ID3v2 タグがあれば読み飛ばす。Ogg FLAC は `UnsupportedFormat`
- ビット深度は 4〜32、チャンネル数は 1〜8、ブロック長は 1〜65536、サンプルレートは STREAMINFO に書ける値すべて
- 位置はフレーム(チャンネルあたりのサンプル)単位で、最初のフレームの先頭を 0 とする。長さは実際のフレームから数え、STREAMINFO の総サンプル数は使わない(書かれていない・間違っているファイルがあるため)

## 2. フレームの区切り

FLAC のフレームヘッダには、フレームの長さが書かれていない。終わりを知るにはサブフレームをすべて読む必要があるが、壊れたフレームでは読めない。そこで次の順で探す(`stream.Iterator`)。

1. 次のフレームヘッダが現れ、そこまでの CRC-16 が合う位置。次のフレームヘッダと認めるのは、同期コード・予約値・CRC-8 が正しく、ストリームの設定(STREAMINFO のサンプルレート・チャンネル数・ビット深度と、最初のフレームのブロック長の方式)と食い違わず、番号が続いているもの。最後のフレームは、入力の終わりで CRC-16 が合う位置
2. 見つからなければ、サブフレームの構造を読んで終わりを求め、そこで CRC-16 が合えばそこまで(最後のフレームの後に ID3v1 タグなどが続く場合)

1 で探す範囲は、そのフレームのすべてのサブフレームが無圧縮だったときの大きさに余裕を足したところまで。ふつうのフレームは 1 で決まる。次のヘッダの候補(0xFF)の間はまとめて CRC-16 を計算するだけなので速い(デコードせずに長さが分かる)。`probe` もこの方法でフレームの区切りをすべて確かめる。

**番号**: 固定ブロック長のフレームの番号はフレーム番号、可変ブロック長ではサンプル位置。ただし、固定ブロック長の印なのに番号がサンプル位置の古い形式もある(Flake 0.11 など)。STREAMINFO のブロック長は誤っていることがあるので使わず、2 つ目のフレームの番号がどちらで続いているかで見分ける。それより前に区切り直すとき(最初か 2 つ目のフレームのヘッダが壊れているなど)は、見つけたヘッダの番号と直前のヘッダの番号(なければ 0)の差がブロック長の倍数ならサンプル位置とみなす。

**区切り直し**: 1 も 2 もだめなフレーム(CRC-16 が合わない)や、ヘッダが読めない位置(ヘッダが壊れている、番号が飛んでいる、フレームの間にゴミがある)からは、番号が次のフレームの番号以上のヘッダで、そのフレームの CRC-16 も合う位置を探して区切り直す(壊れたフレームの中に偶然できた同期コードは、番号か CRC-16 で弾く)。その間は壊れた区間として無音にする。長さは、壊れたフレームのヘッダが読めればそのブロック長に、番号の飛びの分(フレーム番号の差 × 最初のフレームのブロック長、またはサンプル位置の差)を足したもの。番号が飛んでいなければ(フレームの間のゴミ)何も足さずに読み飛ばす。偽のヘッダで長さが際限なく延びないよう、失われた長さには上限を設け、超える候補は区切り直しに使わない。STREAMINFO の総サンプル数が分かればその候補のフレームが総サンプル数より前から始まること、分からなければ 2^20 サンプル(44.1kHz で約 24 秒)まで。区切り直す先が見つからなければ、そこでストリームが終わる(途中で切れた最後のフレームは数えない。MP3 と同じ)。

最初のフレームは、メタデータブロックの直後から始まっているはず(ずれていれば、番号 0 から続くとみなして区切り直す)。ストリームの途中でサンプルレート・チャンネル数・ビット深度が変わる場合は、そこでストリームが終わる(MP3 で途中でチャンネル数が変わる場合と同じ)。

**フレームの一覧**: `decode` / `toWav` は、区切りを探す走査を 1 回だけ行ってフレームの一覧(`kiln.flac.Index`)を作り、それを使って長さを求め、復号する。wasm の `kiln_flac_decode` も `Index` を使い、出力の大きさを決めるための解析と復号で走査を繰り返さない。

## 3. 復号

- サブフレーム(定数、無圧縮、固定予測の次数 0〜4、線形予測の次数 1〜32)、無駄ビット、残差(Rice 符号のパラメータ 4 / 5 ビット、escape)、ステレオの相関除去(left/side、side/right、mid/side)を RFC のとおりに復号する。計算は i64 で行う(32bit の音声の side チャンネルは 33 ビットになるため)
- 出力は整数のまま(`bits_per_sample` ビットの符号付き)で、`sink.writeI32` に渡す。WAV に書くときは `kiln.pcm.fromInt` で変換する
- フレームは互いに独立しているので、区間の先頭を含むフレームから復号すればよい(MP3 のように手前から復号する必要はない)
- 作業領域(チャンネル数 × ブロック長の i64)とフレームの一覧はアロケータで確保する。ブロック長は最大 65536 で、8 チャンネルなら 4MiB になり、wasm のスタックには置けないため。`decode` / `toWav` が `gpa` を受け取るのは MP3 と違う点

**壊れたフレーム**: CRC-16 が合わないフレームや、中身が壊れているフレームは、libFLAC と同じく無音にして続ける。番号の飛びから分かる失われたフレームも無音で埋める(§2)。数は `invalid_frames` で返す(CLI は stderr に警告する。可変ブロック長で失われたフレームは、数が分からないので 1 と数える)。壊れた入力で整数があふれないよう、予測で求めた値がサブフレームのビット数に収まるか、残差が 32 ビットに収まるかを確かめる(正しいストリームでは必ず収まる)。最後に、相関除去の後の値がビット深度に収まるかも確かめる。どれかに反すればそのフレームは壊れているとみなす。

## 4. WAV への書き出し

- 既定の形式はビット深度を保つもの(8bit 以下は `u8`、16bit 以下は `i16`、24bit 以下は `i24`、それより多ければ `i32`)。12bit や 20bit は下位に 0 を足して器のビット数にするので可逆
- `--sample-format`(JS は `format`)で別の形式にもできる。ビット数を減らすとき(24bit → `i16` など)は TPDF ディザで丸める(`--dither` / `dither` で切れる)。浮動小数点へは `値 / 2^(bits - 1)`

## 5. 検証

FLAC の公式テストファイル([ietf-wg-cellar/flac-test-files](https://github.com/ietf-wg-cellar/flac-test-files)、CC0。リポジトリには入れていない)と testdata の 5 本を、kiln で WAV に書き出し、ffmpeg と libFLAC(flac 1.5.0 の `flac -d`)の出力と 32bit 整数に直して比べた。

| 入力 | 結果 |
|---|---|
| testdata の 5 本、subset の 64 本(ブロック長 16〜16384、可変ブロック長(番号がサンプル位置の古い形式を含む)、8 / 12 / 20 / 24bit、1〜8 チャンネル、LPC の次数 32、escape の分割、無駄ビット、大きなメタデータなど) | すべて ffmpeg・libFLAC とビット単位で一致 |
| uncommon の 32bit、768kHz、15bit、ブロック長 65535、Rice の分割の次数 15 | すべて一致 |
| uncommon の途中でサンプルレート・チャンネル数・ビット深度が変わるもの(01〜04) | 変わったところで終わる(既知の差) |
| uncommon の `fLaC` がなくフレームから始まるもの(10、11) | `NotFlac`(既知の差。ストリーミングで受け取った途中からのフレーム列は扱わない) |
| faulty(STREAMINFO の誤りなど) | STREAMINFO がない・先頭にない・ブロックの長さが不正なものは `InvalidFlac`。STREAMINFO のビット深度・チャンネル数がフレームと違うものはフレームが 0 個(`EmptyRange`)。最大ブロック長の誤り・ブロック長 1 は libFLAC と一致、総サンプル数の誤りは ffmpeg と一致(実際のフレームから数えるため) |

testdata の FLAC から書いた WAV は、元にした WAV と PCM が一致する(テスト)。また、49 秒の曲を FLAC にして kiln で WAV に戻すと、`flac -d` の出力とファイル全体でバイト単位で一致した。

壊れた入力: 公式テストファイルと testdata の FLAC のバイトを反転・上書き・切り詰めたもの 800 本を Debug ビルド(安全検査あり)の CLI に通し、パニックしないことを確かめた。1 フレームの中身かヘッダを壊したとき、1 フレームをまるごと取り除いたとき、壊れたフレームの中に次のフレームと同じヘッダを書き込んだときのどれでも、そのフレームの分だけが無音になり、長さとほかのフレームは元と同じになる。番号がサンプル位置の形式で最初・2 つ目・途中のフレームのヘッダを壊したときも同じ。番号を 10 億に書き換えた(CRC は正しい)フレームでは区切り直さず、そこで終わる(テスト)。

速さ: 49 秒の 16bit ステレオの曲を WAV にするのに、ReleaseFast で 0.1 秒(`flac -d` は 0.05 秒)。15 秒の 8 チャンネル・192kHz・24bit(公式テストファイル 44)は ReleaseFast で 0.65 秒、wasm(ReleaseSmall、Node)で 1.0 秒(Apple Silicon の Mac)。

## 6. 書き出し(エンコーダ)

`kiln.flac.Encoder`(`src/flac/encoder.zig`、LPC の分析は `src/flac/lpc.zig`)。仕様は RFC 9639、手順の考え方と既定値(段階ごとの設定、LPC の係数のビット数、次数の見積もり)は libFLAC(BSD-3-Clause)に倣った。コードや表は写していない。

### 6.1 出力の構成

- `fLaC`、STREAMINFO、Vorbis コメント(ベンダー文字列 `kiln <バージョン>` だけ)の順に書き、その後にフレームが続く。PADDING とシークテーブルは書かない
- フレームはすべて固定ブロック長(番号はフレーム番号)。ブロック長は段階で決まり(1152 か 4096)、最後のフレームだけ短い
- フレームヘッダのサンプルレートとビット深度は、ヘッダの符号で書けるものは書き、書けないもの(768kHz、15bit など)は STREAMINFO を参照する符号(0)にする
- STREAMINFO の総サンプル数・フレームの大きさの最小と最大・MD5 は書き終えるまで決まらない。`finish` が STREAMINFO のバイト列と位置を返し、呼び出し側が出力の先頭に書き戻す(`docs/architecture.md` §2 の方針)。`kiln.wav.toFlac` / `kiln.mp3.toFlac` は `*Io.Writer` に流して書き、書き戻しを返す。一括版(`toFlacAlloc` / `encodePlanarAlloc`)はメモリ上で書き戻す。CLI は、ファイルへはフレームを流して書いてから位置を指定して書き戻し(出力全体をメモリにためない)、stdout へはメモリ上で書き戻してから書く
- MD5 は、各サンプルを (ビット深度 + 7) / 8 バイトのリトルエンディアンの符号付き整数にして並べたものから計算する(RFC 9639 §8.2)

### 6.2 圧縮の段階

flac コマンドの -0〜-8(flac 1.5)と同じ設定にした。既定は 5。

| 段階 | ブロック長 | LPC の最大次数 | ステレオ | Rice の分割の最大次数 | 窓関数 |
|---|---|---|---|---|---|
| 0 | 1152 | なし(固定予測だけ) | 独立 | 3 | — |
| 1 | 1152 | なし | 見積もりで選ぶ | 3 | — |
| 2 | 1152 | なし | すべて試す | 3 | — |
| 3 | 4096 | 6 | 独立 | 4 | Tukey(0.5) |
| 4 | 4096 | 8 | 見積もりで選ぶ | 4 | Tukey(0.5) |
| 5 | 4096 | 8 | すべて試す | 5 | Tukey(0.5) |
| 6 | 4096 | 8 | すべて試す | 6 | subdivide_tukey(2) |
| 7 | 4096 | 12 | すべて試す | 6 | subdivide_tukey(2) |
| 8 | 4096 | 12 | すべて試す | 6 | subdivide_tukey(3) |

- ステレオの「すべて試す」は、左右・左と side・side と右・mid と side の 4 通りを符号化して最小のものを選ぶ(flac の -m)。「見積もりで選ぶ」は、4 つの信号の固定予測の残差の大きさで方式を選び、その 2 つだけを符号化する(flac の -M に相当)。3 チャンネル以上は独立
- subdivide_tukey(N) は、ブロック全体の Tukey 窓に、2〜N 等分した各部分の Tukey 窓と、3〜N 等分した各部分をくり抜いた窓を足したもの(N = 2 で 3 つ、N = 3 で 9 つ)。なだらかな縁の長さは、いちばん小さい部分に Tukey(0.5) を当てたときと同じにする

### 6.3 サブフレームの選び方

チャンネル(または side / mid)ごとに、次のうち最も小さくなるものを選ぶ。

1. **無駄ビット**: すべてのサンプルの下位で 0 のビットを除く
2. **定数**: すべて同じ値なら定数のサブフレーム
3. **無圧縮**: 比較の基準(どの方法もこれより大きければ無圧縮)
4. **固定予測**: 次数 0〜4 のうち、残差の絶対値の和が最小の次数
5. **線形予測**(段階 3 以上): 窓ごとに、窓を掛けた信号の自己相関から Levinson-Durbin で係数を求め、予測誤差から見込みのビット数が最小になる次数を選ぶ。ほぼ完全に予測できる信号では、丸め誤差で反射係数の絶対値が 1 以上(誤差が負)になることがあるので、その次数より手前までを候補にする。係数は libFLAC の既定と同じビット数(16bit の音声でブロック長 4096 なら 12 ビット)で、丸め誤差を次の係数に持ち越して量子化する。ビット深度が 17 以下では、32 ビットの整数で予測を計算するデコーダでもあふれないよう係数のビット数を抑える

固定予測と線形予測の残差は 32 ビットの符号付き整数に収まらなければならない(RFC 9639 §9.2.7)。32bit の音声や 33 ビットの side チャンネルではあふれうる(満幅の矩形波など)ので、収まらない候補は使わない(テスト)

残差は Rice 符号で書く。分割の次数ごとに、各分割の残差の和から見積もりのビット数が最小のパラメータを求め、合計が最小の次数を選ぶ。選んだ次数では、各分割のパラメータを前後 1 つずつ正確なビット数で比べて決め直す。

### 6.4 入力とビット深度

- **整数の WAV**(`kiln.wav.toFlac` / `toFlacAlloc`、CLI の WAV → FLAC): 既定では元のビット深度のまま書くので可逆。8bit の WAV(符号なし)は符号付きの 8bit にする
- **浮動小数点**(浮動小数点の WAV、MP3 のデコード結果、JS の AudioBuffer): 既定は 16bit で、TPDF ディザで丸める(`kiln.pcm.quantizeBits`)。64bit 浮動小数点の WAV は f32 を経由する
- **ビット深度の指定**(CLI の `--bits`、JS の `bitsPerSample`、4〜32): 整数の入力で元より多ければ下位に 0 を足し(可逆)、少なければディザで丸める
- チャンネル数は 1〜8、サンプルレートは 1〜1048575 Hz(STREAMINFO に書ける範囲)。外れれば `InvalidOptions`

### 6.5 検証

- **往復**: testdata の WAV 4 本(8 / 16 / 24 / 32bit、1〜3 チャンネル)をすべての段階で FLAC にして kiln で復号すると、元の PCM と一致する(テスト)。端のケース(ビット深度 4〜32、1〜3 チャンネル、長さ 1〜5000、雑音・無音・満幅の正負の交互・ランプ、ヘッダに書けないサンプルレート)も往復で一致する(テスト)
- **libFLAC と ffmpeg**: 次のどれも `flac -t`(MD5 の確認を含む)が通り、ffmpeg で復号した PCM が元と一致した
  - 曲(49 秒の 16bit ステレオ)、24bit 96kHz、モノラル、8 チャンネル、8bit を、すべての段階で FLAC にしたもの
  - 端のケース 720 通り(8 / 16 / 24 / 32bit × 1 / 2 / 3 / 8 チャンネル × 長さ 1〜9000 × 雑音・満幅・無音 × 段階 0 / 5 / 8。Debug ビルドの CLI)
  - JS の `flac.encode` / `wav.toFlac` / `mp3.toFlac` の出力
- **大きさ**: flac 1.5(`--no-padding --no-seektable`)と同じ段階で比べると、曲・24bit・モノラル・8 チャンネルは -0.3〜+0.1%、8bit は -2.2〜+0.1% の差。たとえば曲は 5 で 3,642,512 バイト(flac は 3,642,850)、8 で 3,523,344 バイト(flac は 3,523,776)
- **速さ**(Apple Silicon の Mac): 49 秒の曲で、段階 0 は 0.07 秒、5 は 0.15 秒、8 は 0.85 秒(flac はそれぞれ 0.04 / 0.06 / 0.14 秒)。wasm(ReleaseSmall、Node)は 0.10 / 0.20 / 0.89 秒。2 分 43 秒の MP3 を FLAC にするのは 0.9 秒(デコードを含む)
