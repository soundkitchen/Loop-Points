# K!LN (repo: `kiln`) — Claude Code 引き継ぎドラフト

> 状態: 検討段階。方向性だけ決まっていて、設計・スコープ・実装順はこれから Claude Code と議論して決める。
> 下の「見立て」はここまでの会話で出た案であって、決定ではない。反対意見や別案は歓迎。

## 1. 目的と動機

複数の音声形式をエンコード(必要ならデコード)できるライブラリを **Zig** で自作し、**ブラウザ(wasm)** で使えるようにする。CLI からも使えると嬉しい。

きっかけ: Google Gemini Lyria が書き出す MP3 を切り出し(crop)したい。最低でも MP3 を書き出せるようにしておきたい。

## 2. 決まっていること(これだけ)

- 言語は Zig。
- プロジェクト名は `K!LN`、リポジトリ名は `kiln`(`!` は識別子に使えないため、表示名と識別子を分ける)。
- ブラウザで使えるよう wasm 対応する。

### 2.1 2026-11-09 に決めたこと

- **目的の整理**: 主機能は「任意の音声を読み込み、クロップして、任意の形式で書き出す」こと(デコード → PCM → クロップ → エンコード)。最初の具体的な対象は Lyria の MP3。
- **最初の到達点**: MP3 → MP3 の無劣化・サンプル精度トリム。方式と検証結果は [`lyria-mp3.md`](lyria-mp3.md)。汎用パイプラインに付け足す「同一形式なら再エンコードしない」最適化と位置づける。
- **最初に動かす環境**: CLI と wasm の両方。コアは I/O を持たず、CLI と wasm は薄いラッパーにする。
- **C2PA マニフェスト**: トリムすると検証に失敗するため、常に削除する(ID3v2 タグ自体は `iTunSMPB` のために付ける)。
- **リポジトリ**: このディレクトリ(クラウド同期フォルダ内)に git リポジトリを作る。
- **Zig のバージョン**: 0.17.1。`.envrc`(direnv)で `~/Zig/0.17` を PATH に通す。
- **テスト用の音声**: Lyria の実ファイル(`samples/`)は git に入れない。テストには lame で作った、Lyria と同じ構成(CBR 192kbps、Xing なし)の短い MP3 を使い、リポジトリに入れる。
- **MP3 トリムで付ける LAME タグのエンコーダ名**: `LAMEK!LN`。`LAME` で始めるのは ffmpeg / Chrome に delay / padding を読ませるため。
- **Safari 対応**: トリム結果に ID3v2 の `iTunSMPB` を付け、末尾に 1 フレーム余分に含める(詳細は [`lyria-mp3.md`](lyria-mp3.md))。Firefox の確認は後回し。
- **コア API**: [`architecture.md`](architecture.md) の方針で進める。

## 3. まだ決めていないこと(論点と、ここまでの見立て)

### 3.1 スコープ: 何をいつサポートするか

最初に挙がった対象は `.wav .aiff .mp3 .flac .webm .ogg`。ただし `.ogg` と `.webm` はコンテナで、中身のコーデック(Vorbis / Opus)の選択が別に要る。

見立て(要議論):
- WAV / AIFF → FLAC → Ogg コンテナ → MP3 → Opus/Vorbis、の順が実装しやすい。
- FLAC は可逆なので、エンコード → デコードのビット一致で正しさを機械的に確認できる。最初の本命にしやすい。
- Opus は実装が大きい。from scratch にこだわるかどうかで方針が変わる。

### 3.2 入力側: デコーダを自前で持つか

- ブラウザだけなら `decodeAudioData` で PCM を得られるので、**エンコーダ専用**で済み、デコーダ・デミックス・形式判定が不要になる。
- CLI を作るなら、ブラウザのデコード機能がないため自前デコーダが必要になる場面が出る(MP3 → WAV など)。

見立て: 最初はブラウザ向けエンコード専用に絞り、CLI とデコーダは後から足す案。CLI を最初から入れるかは未定。

### 3.3 MP3 の切り出し方式

- (A) **無劣化のフレーム単位トリム**: 再エンコードなし、エンコーダ不要。精度は約 26ms。ビットリザーバ(先頭フレームが前のフレームに依存する)と Xing/LAME ヘッダ更新に注意が必要。
- (B) デコード → 切り出し → 再エンコード: サンプル精度やフェード焼き込みができるが、世代劣化があり、MP3 エンコーダが必須。

見立て: Lyria 出力を切るだけなら (A) が軽くて効果が高い。ただし、実際のファイル(ビットレート、CBR/VBR、タグ構成)を見てから決めたい。MP3 エンコーダを入れる優先度も、この結果しだいで変わる。

### 3.4 アーキテクチャ

見立て:
- コアは I/O を持たず、アロケータとバイト列/サンプル列を受け取る。CLI と wasm はその薄いラッパー。
- コーデックとコンテナの型を分ける(Ogg と WebM の両方に Opus を載せられるように)。
- 形式判定は拡張子ではなくマジックバイト。
- wasm は `wasm32-freestanding`、JS 側が linear memory にサンプルを書いてポインタと長さを渡す形。

ディレクトリ構成、API の形(ストリーミングか一括か)、エラー処理の方針などは未定。

### 3.5 テスト・検証

見立て: ffmpeg や `flac` CLI との突き合わせ、FLAC 公式テストファイル、パーサ側のファズ。具体的な仕組み(CI をどうするか等)は未定。

## 4. 調べて分かった事実(判断材料)

- **Zig の最新安定版は 0.17.1**(2026-11-02、公式ダウンロードページで確認)。Zig は 1.0 前で破壊的変更が入りやすい。0.16 以前の記事やライブラリのコードは API が違う可能性があるので、写す前に 0.17 のリリースノートと標準ライブラリのドキュメントで確認すること。バージョン固定をどうするかは未定。
- Zig にはパッケージマネージャが組み込まれている(`build.zig.zon` + `zig fetch --save`)。中央レジストリはなく、名前の衝突は問題になりにくい。
- 参考になりそうな既存物:
  - Zig 製の FLAC デコーダ(pure Zig、FLAC 公式テストスイートで検証済み): `zff.dev/audiophile/flac`
  - Zig 製の音声ライブラリ `braheezy/zigaudio`(wav / flac / mp3 / ogg / aac などの読み書きを目指している)
  - Rust の Symphonia(デコード専用、pure Rust): デコード結果の比較対象に使える
  - npm の `audio` パッケージ(JS/CLI で trim して mp3 などに保存できる)は用途が近い先行例。差別化は「小さな Zig コアが CLI と wasm の両方で動く」ことと、MP3 の無劣化トリムあたりか。
- crates.io の `kiln` は別のデータベース crate が使用中。Rust 版を出す場合は別名にする必要がある。npm の `kiln` の空きは未確認。
- ブラウザ側の制約:
  - `decodeAudioData` の出力は AudioContext のサンプルレートにリサンプルされる。
  - 長尺音声はメモリが大きい(float32 ステレオ 44.1kHz の 10 分で約 210MB)。
  - 出力時の量子化(16/24bit 化)でディザを使うかは未定。
  - Safari の Ogg 対応は 18.4 以降で改善したとされるが、Ogg Opus は不完全という報告もある。

## 5. 注意事項

- **AAC のライセンス**: Via LA の特許プールが、AAC のエンコーダ・デコーダを含む最終製品のメーカー/開発者にライセンスを求めている。AAC-LC の特許は失効したという見方が有力(Red Hat が 2017 年に判断)だが、国ごとに満了時期が異なり公的な宣言はない。HE-AAC v2 や xHE-AAC は有効とされる。扱うなら feature flag でデフォルト無効にするのが無難。商用利用や配布を考える段階で専門家に確認すること。MP3 の特許は米国・EU で失効済み。
- MP3 は先頭にエンコーダ遅延ぶんの無音が入る形式で、補正情報(LAME タグ)をプレイヤーが読むかは環境しだい。ループや厳密なタイミングが要る用途には WAV か Opus が向く。
