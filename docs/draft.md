# K!LN (repo: `kiln`) — Claude Code 引き継ぎドラフト

> 状態: 検討段階。方向性だけ決まっていて、設計・スコープ・実装順はこれから Claude Code と議論して決める。
> 下の「見立て」はここまでの会話で出た案であって、決定ではない。反対意見や別案は歓迎。

## 1. 目的と動機

複数の音声形式をエンコード(必要ならデコード)できるライブラリを **Zig** で自作し、**ブラウザ(wasm)** で使えるようにする。CLI からも使えると嬉しい。

きっかけ: Google Gemini Lyria が書き出す MP3 を切り出し(crop)したい。最低でも MP3 を書き出せるようにしておきたい。

## 2. 決まっていること(これだけ)

- 言語は Zig。
- プロジェクト名は `K!LN`、リポジトリ名は `kiln`(`!` は識別子に使えないため、表示名と識別子を分ける)。
- ブラウザで使えるよう wasm 対応する。

### 2.1 2026-11-09 に決めたこと

- **目的の整理**: 主機能は「任意の音声を読み込み、クロップして、任意の形式で書き出す」こと(デコード → PCM → クロップ → エンコード)。最初の具体的な対象は Lyria の MP3。
- **最初の到達点**: MP3 → MP3 の無劣化・サンプル精度トリム。方式と検証結果は [`lyria-mp3.md`](lyria-mp3.md)。汎用パイプラインに付け足す「同一形式なら再エンコードしない」最適化と位置づける。
- **最初に動かす環境**: CLI と wasm の両方。コアは I/O を持たず、CLI と wasm は薄いラッパーにする。
- **C2PA マニフェスト**: トリムすると検証に失敗するため、常に削除する(ID3v2 タグ自体は `iTunSMPB` のために付ける)。
- **リポジトリ**: このディレクトリ(クラウド同期フォルダ内)に git リポジトリを作る。
- **Zig のバージョン**: 0.17.1。`.envrc`(direnv)で `~/Zig/0.17` を PATH に通す。
- **テスト用の音声**: Lyria の実ファイル(`samples/`)は git に入れない。テストには lame で作った、Lyria と同じ構成(CBR 192kbps、Xing なし)の短い MP3 を使い、リポジトリに入れる。
- **MP3 トリムで付ける LAME タグのエンコーダ名**: `LAMEK!LN `(末尾の空白を含めて 9 バイト。LAME タグのこのフィールドは 9 バイト固定)。`LAME` で始めるのは ffmpeg / Chrome に delay / padding を読ませるため。
- **Safari 対応**: トリム結果に ID3v2 の `iTunSMPB` を付ける(値は LAME タグの delay / padding と同じ。詳細は [`lyria-mp3.md`](lyria-mp3.md) §4)。当初は priming に 529 を足し、末尾に 1 フレーム余分に含めていたが、同じ日の再確認で直した(§2.3)。
- **コア API**: [`architecture.md`](architecture.md) の方針で進める。

### 2.2 2026-11-09 に決めたこと(MP3 トリマーの実装)

- **CLI**: サブコマンド形式。`kiln trim <input> <output> [--start TIME] [--end TIME | --duration TIME]`。`-` で stdin / stdout
- **時刻の指定**: 秒(`1.5`)、`分:秒`(`1:02.5`)、サンプル数(`66150s`)のどれでもよい。秒はサンプル位置に切り捨てで変換する
- **範囲外の指定**: 丸めて続行する(タグなしの入力では先頭を 529 サンプルに切り上げ、末尾はファイルの終わりに切り詰める)。丸めたことは CLI が stderr に警告する。丸めた結果が空ならエラー
- **入力の範囲**: MPEG-1 Layer III なら、Xing / LAME タグ付き(他のエンコーダの出力)も受け付ける。位置は ffmpeg がデコードしたときの先頭を 0 とする(LAME タグの delay を除いた位置)。MPEG-2 / 2.5 は扱わない
- **API**: `kiln.mp3.probe` / `trim`(`*std.Io.Writer` に書く)/ `trimAlloc`。範囲外の丸めはコアが行い、実際に切り出した区間を返す。JS は `mp3.probe` / `mp3.trim`(秒またはサンプル数)。詳細は [`architecture.md`](architecture.md) §2.1〜2.3
- **低ビットレートの入力**: 開始位置の手前に必要なフレームが LAME タグの delay(12bit)に収まらないときだけ、ビットリザーバの中身を詰めた無音フレーム(carrier)を使う。Lyria のような入力では従来どおり元のフレームだけを連結する(詳細は [`lyria-mp3.md`](lyria-mp3.md) §5.2)

### 2.3 2026-11-09 に決めたこと(MP3 トリムの再生確認)

- **`iTunSMPB` の値**: priming / padding を LAME タグの delay / padding と同じ値にする(以前は `delay + 529` / `padding - 529`)。CoreAudio(Safari)はデコーダ遅延の 529 を除いた出力に `iTunSMPB` を当てるため、529 を足すと 529 サンプル余分に落としていた。これで Safari でも ffmpeg / Chrome / Firefox と同じ位置・長さになる
- **末尾のフレーム**: 最後のサンプルを含むフレームまでにする(以前は Safari 向けに 1 フレーム余分に含めていた。余分に落としていた 529 サンプルを補うためのもので、不要になった)。padding が 0 にならないので、Safari の `<audio>` も `iTunSMPB` を使う
- **既知の差として残すもの**: Safari などデコーダ遅延を隠すデコーダは、タグのない元ファイル(Lyria の出力を含む)を ffmpeg より 529 サンプル前にずらして再生する。位置の基準は ffmpeg のまま変えない(詳細は [`lyria-mp3.md`](lyria-mp3.md) §6)
- **Firefox と `<audio>` 要素**: Chrome / Firefox / Safari で確認した(結果は [`lyria-mp3.md`](lyria-mp3.md) §5.4)

### 2.4 2026-11-09 に決めたこと(WAV と MP3 デコーダ)

- **範囲**: WAV の読み込み・サンプル精度の切り出し・書き出しと、MP3 デコーダ(MPEG-1 Layer III)を作る。PR は WAV(`feature/wav`)と MP3 デコーダ(`feature/mp3-decoder`)に分ける
- **PCM の表し方**: 読み込んだ元の形式(8bit 符号なし、16 / 24 / 32bit 整数、32 / 64bit 浮動小数点)のまま持ち、必要なときだけ変換する。WAV → WAV はビット一致にする
- **ディザ**: 浮動小数点から整数にするときは、既定で TPDF ディザをかける(乱数の種は固定)。オプションで切れる。WAV → WAV のように形式を変えないときは関係しない
- **CLI の出力形式**: `--format wav|mp3` で指定する。省くと入力と同じ形式。MP3 エンコーダはないので、MP3 以外 → MP3 はエラー
- **MP3 → WAV の既定の形式**: 16bit 整数(オプションで変えられる)
- **ライセンスの方針**: できるだけ MIT に近づける。MP3 デコーダの規格の数表(ハフマン符号表、合成窓)は、CC0 の minimp3 から取る(LGPL の ffmpeg からは取らない。[`mp3-decoder.md`](mp3-decoder.md) §1)

### 2.6 2026-11-10 に決めたこと(FLAC)

- **範囲**: デコーダとエンコーダの両方を作る(FLAC → WAV、FLAC → FLAC の切り出し、WAV / MP3 / AudioBuffer → FLAC)。PR はデコーダ(`feature/flac-decoder`)、エンコーダ(`feature/flac-encoder`)、FLAC → FLAC の切り出し(`feature/flac-trim`)の 3 つに分ける(エンコーダと切り出しを分けることは、エンコーダに取りかかるときに決めた)
- **FLAC → FLAC の切り出し**: 区間の先頭と末尾にかかるフレームだけ作り直し、ほかのフレームはそのままコピーする(元の圧縮率を保つ)。どちらにしても復号した PCM は元と同じ
- **エンコーダの圧縮**: 線形予測(LPC)と Rice 符号のパラメータ探索まで作り、flac の既定(-5)に近い大きさを目標にする。圧縮の段階は flac / sox / Audacity などと同じ 0〜8(既定 5)から選べ、中身も flac の -0〜-8 に合わせる(ffmpeg は 0〜12)。CLI は `--compression N`、JS は `compression`
- **書き出すビット深度**: 整数の WAV は元のビット深度、浮動小数点の入力(MP3 のデコード結果、AudioBuffer、浮動小数点の WAV)は既定で 16bit(TPDF ディザ)。CLI は FLAC 専用の `--bits N`(4〜32。`--sample-format` は WAV 用のまま)、JS は `bitsPerSample`
- **JS の API**: 入力ごとに分ける(`flac.encode(AudioBuffer か Float32Array[])`、`wav.toFlac`、`mp3.toFlac`、`flac.trim`)
- **MD5**: 書き出す FLAC の STREAMINFO に PCM の MD5 を入れる(FLAC → FLAC の切り出しでも、区間をすべて復号して計算する)
- **メタデータ**: FLAC → FLAC では Vorbis コメント・画像・APPLICATION を残し、STREAMINFO(長さと MD5)は作り直す。シークテーブルと CUE シートは位置がずれるので捨てる
- **検証**: 参照実装の `flac` / `metaflac`(Homebrew)と ffmpeg、FLAC の公式テストファイル(CC0、リポジトリには入れない)と突き合わせる。テスト用の FLAC は `flac` で作ってリポジトリに入れる
- **デコーダの細部**(設計は [`flac.md`](flac.md)): 仕様は RFC 9639 から自分で書く。Ogg FLAC は扱わない。FLAC → WAV の既定の形式はビット深度を保つもの(可逆)。CRC が合わないなど壊れたフレームは、libFLAC と同じく無音にして数を返す

## 3. まだ決めていないこと(論点と、ここまでの見立て)

### 3.1 スコープ: 何をいつサポートするか

最初に挙がった対象は `.wav .aiff .mp3 .flac .webm .ogg`。ただし `.ogg` と `.webm` はコンテナで、中身のコーデック(Vorbis / Opus)の選択が別に要る。

見立て(要議論):
- WAV / AIFF → FLAC → Ogg コンテナ → MP3 → Opus/Vorbis、の順が実装しやすい。
- FLAC は可逆なので、エンコード → デコードのビット一致で正しさを機械的に確認できる。最初の本命にしやすい。
- Opus は実装が大きい。from scratch にこだわるかどうかで方針が変わる。

### 3.2 入力側: デコーダを自前で持つか

- ブラウザだけなら `decodeAudioData` で PCM を得られるので、**エンコーダ専用**で済み、デコーダ・デミックス・形式判定が不要になる。
- CLI を作るなら、ブラウザのデコード機能がないため自前デコーダが必要になる場面が出る(MP3 → WAV など)。

見立て: 最初はブラウザ向けエンコード専用に絞り、CLI とデコーダは後から足す案。CLI を最初から入れるかは未定。

### 3.3 MP3 の切り出し方式

- (A) **無劣化のフレーム単位トリム**: 再エンコードなし、エンコーダ不要。精度は約 26ms。ビットリザーバ(先頭フレームが前のフレームに依存する)と Xing/LAME ヘッダ更新に注意が必要。
- (B) デコード → 切り出し → 再エンコード: サンプル精度やフェード焼き込みができるが、世代劣化があり、MP3 エンコーダが必須。

見立て: Lyria 出力を切るだけなら (A) が軽くて効果が高い。ただし、実際のファイル(ビットレート、CBR/VBR、タグ構成)を見てから決めたい。MP3 エンコーダを入れる優先度も、この結果しだいで変わる。

### 3.4 アーキテクチャ

見立て:
- コアは I/O を持たず、アロケータとバイト列/サンプル列を受け取る。CLI と wasm はその薄いラッパー。
- コーデックとコンテナの型を分ける(Ogg と WebM の両方に Opus を載せられるように)。
- 形式判定は拡張子ではなくマジックバイト。
- wasm は `wasm32-freestanding`、JS 側が linear memory にサンプルを書いてポインタと長さを渡す形。

ディレクトリ構成、API の形(ストリーミングか一括か)、エラー処理の方針などは未定。

### 3.5 テスト・検証

見立て: ffmpeg や `flac` CLI との突き合わせ、FLAC 公式テストファイル、パーサ側のファズ。具体的な仕組み(CI をどうするか等)は未定。

## 4. 調べて分かった事実(判断材料)

- **Zig の最新安定版は 0.17.1**(2026-11-02、公式ダウンロードページで確認)。Zig は 1.0 前で破壊的変更が入りやすい。0.16 以前の記事やライブラリのコードは API が違う可能性があるので、写す前に 0.17 のリリースノートと標準ライブラリのドキュメントで確認すること。バージョン固定をどうするかは未定。
- Zig にはパッケージマネージャが組み込まれている(`build.zig.zon` + `zig fetch --save`)。中央レジストリはなく、名前の衝突は問題になりにくい。
- 参考になりそうな既存物:
  - Zig 製の FLAC デコーダ(pure Zig、FLAC 公式テストスイートで検証済み): `zff.dev/audiophile/flac`
  - Zig 製の音声ライブラリ `braheezy/zigaudio`(wav / flac / mp3 / ogg / aac などの読み書きを目指している)
  - Rust の Symphonia(デコード専用、pure Rust): デコード結果の比較対象に使える
  - npm の `audio` パッケージ(JS/CLI で trim して mp3 などに保存できる)は用途が近い先行例。差別化は「小さな Zig コアが CLI と wasm の両方で動く」ことと、MP3 の無劣化トリムあたりか。
- crates.io の `kiln` は別のデータベース crate が使用中。Rust 版を出す場合は別名にする必要がある。npm の `kiln` の空きは未確認。
- ブラウザ側の制約:
  - `decodeAudioData` の出力は AudioContext のサンプルレートにリサンプルされる。
  - 長尺音声はメモリが大きい(float32 ステレオ 44.1kHz の 10 分で約 210MB)。
  - 出力時の量子化(16/24bit 化)でディザを使うかは未定。
  - Safari の Ogg 対応は 18.4 以降で改善したとされるが、Ogg Opus は不完全という報告もある。

## 5. 注意事項

- **AAC のライセンス**: Via LA の特許プールが、AAC のエンコーダ・デコーダを含む最終製品のメーカー/開発者にライセンスを求めている。AAC-LC の特許は失効したという見方が有力(Red Hat が 2017 年に判断)だが、国ごとに満了時期が異なり公的な宣言はない。HE-AAC v2 や xHE-AAC は有効とされる。扱うなら feature flag でデフォルト無効にするのが無難。商用利用や配布を考える段階で専門家に確認すること。MP3 の特許は米国・EU で失効済み。
- MP3 は先頭にエンコーダ遅延ぶんの無音が入る形式で、補正情報(LAME タグ)をプレイヤーが読むかは環境しだい。ループや厳密なタイミングが要る用途には WAV か Opus が向く。
